# ADR 0002: Authentication: Auth.js Credentials + JWT sessions

- **Status:** Accepted (implemented in #69; sign-up page in #84, sign-in page in #82)
- **Date:** 2026-10-11
- **Task:** T-06 (auth mechanism) · delivers US-01 (sign-up), US-02 (sign-in), supports US-03 (sign-out)
- **See also:** [backend contract](../../dovivo_backend_contract.pdf) §4 (`User` fields and the
  "Important" box), §7 (S1 procedures), §10 #3 (Credentials required, OAuth optional)

## Context

- US-01 / US-02 require **email + password** accounts. The PO backlog assumes Laravel Sanctum
  (`personal_access_tokens`, token deleted on sign-out).
- The skeleton used Auth.js v5 (beta.25) with the Prisma adapter, **database** sessions and an
  optional Discord provider. As the contract (§4) notes, Auth.js's Credentials provider **only
  works with the JWT session strategy**.
- Auth must not leak whether an email is registered, and blocked users (`blockedAt`, set by an
  admin) must not be able to sign in or publish.

The contract summarises auth; this ADR records the detailed decisions and their trade-offs.

## Decision

| Topic | Decision |
| --- | --- |
| Provider | Auth.js **Credentials** (email + password), always on. Discord stays optional (enabled only if `AUTH_DISCORD_*` is set) |
| Session | `session: { strategy: "jwt" }`: signed, encrypted JWT in an HttpOnly cookie; the `Session` table is unused. The `jwt` callback copies `id` and `role` into the token at sign-in and **fails closed** (throws) if either is missing; `sessionCallback` exposes them as `session.user.id` / `.role` |
| Code layout | `src/server/auth/callbacks.ts` holds `createAuthorize`, `signInCallback`, `createJwtCallback`, `sessionCallback` with dependencies passed in (tested without a DB); `config.ts` only wires them |
| Adapter | Prisma adapter kept so OAuth accounts (`Account` table) still work |
| Hashing | `bcryptjs` (pure JS, works on every OS), cost **12**. Stored in `User.passwordHash` (null for OAuth-only users) |
| Hash never leaks | `passwordHash` is excluded globally via Prisma `omit` (`src/server/db-omit.ts`, applied in `src/server/db.ts`); only `authorizeCredentials` selects it explicitly |
| Password rules | Min **8 characters** (`PASSWORD_MIN_LENGTH`, sign-up only; sign-in just requires non-empty) and max **72 bytes in UTF-8** (`PASSWORD_MAX_BYTES`, one refine in both `signUpSchema` and `signInSchema`; accented letters and emoji count as more than one byte). bcrypt ignores everything after 72 bytes. Both constants are exported from `src/lib/validators/auth.ts` for the UI |
| Sign-up | tRPC `auth.signUp` (public mutation). Email trimmed + lowercased; `User.email` is `citext`, so uniqueness ignores case for every sign-up path (OAuth emails included). Duplicate email → `CONFLICT` (also when two sign-ups race: Prisma `P2002` → `CONFLICT`). Returns `{ id, name, email }`; the client then calls `signIn("credentials")` |
| Sign-in | `signIn("credentials", …)` → `authorize` (`createAuthorize`) → rate limit → `authorizeCredentials()` in `src/server/services/auth.ts`. Returns `null` → generic `CredentialsSignin` (`code: "credentials"`) for invalid input, unknown email, OAuth-only account, wrong password or blocked account |
| User enumeration | Same error for every credential failure. Unknown email → bcrypt compare against a **dummy hash**; the blocked check runs after the password compare. Response time doesn't reveal registered or blocked emails |
| Blocked / deleted users | Credentials: refused by `authorizeCredentials` (generic error). OAuth: refused by `signInCallback` (`AccessDenied`). A JWT stays valid until it expires (contract §4), so the `jwt` callback (`createJwtCallback`) loads `{ blockedAt, role }` by primary key on every `auth()` call; missing or blocked → it returns `null`, Auth.js drops the session and clears the cookie. Blocking or deleting the account (US-07 hard delete) takes effect on the next request everywhere: tRPC (`protectedProcedure` → `UNAUTHORIZED`), server components and `/api/auth/session` |
| Role freshness | The same `jwt` callback refreshes `role` from the DB on every request, so `session.user.role` is current in tRPC (and an `adminProcedure` built on `protectedProcedure`) and in server components |
| Sign-out | `signOut()` (Auth.js) clears the session cookie |
| Rate limiting | See below |
| Sign-in page | Our `/login` page (#82). `pages: { signIn: "/login" }`, so Auth.js's own sign-in redirects and `/api/auth/signin` land there too. `callbackUrl` is sanitised with `safeCallbackUrl` (`src/app/_lib/`): only same-origin paths, parsed with `URL` |

### Rate limiting (`src/server/services/rate-limit.ts`)

In-memory fixed windows of 15 minutes:

| Action | Limit | Key | Result when exceeded |
| --- | --- | --- | --- |
| Sign-up | 5 / 15 min | client IP (skipped if the IP is unknown) | `TOO_MANY_REQUESTS` |
| Sign-in | 30 failed / 15 min | client IP, across all emails (skipped if the IP is unknown) | `RateLimitedSignin` → `res.code === "rate_limited"` |
| Sign-in | 10 failed / 15 min | email, from any IP | same |

- Sign-in limits are checked **before** the user lookup, so `rate_limited` doesn't reveal
  whether the account exists. No separate IP + email limiter (the per-email limit already caps
  every pair) and no shared bucket for unknown IPs.
- **Only failed sign-ins count.** Every attempt is counted up front (so parallel guesses can't
  all slip through during the slow bcrypt check) and handed back with `refundSignInAttempt`
  when it succeeds. The owner never uses up their own attempts, and users behind one shared IP
  can still sign in.
- **Client IP**: `getClientIp(headers, TRUSTED_PROXY_COUNT)` reads `X-Forwarded-For` from the
  right. `TRUSTED_PROXY_COUNT` (env, default `0`) is the number of reverse proxies in front of
  the app: with `N ≥ 1` it takes the entry `N` positions from the right. With `0` (no proxy)
  the IP is **unknown** (`null`): every forwarding header could come from the client, so per-IP
  limits are off and only the per-email sign-in limit applies. Missing header or fewer entries
  than expected → `null`. `X-Real-IP` is never used. Set it to the real proxy count on
  staging/production.

Business logic lives in pure functions that receive the DB as a parameter and are unit-tested
with Vitest and a fake DB.

## Consequences

**Positive**

- Meets US-01/US-02 acceptance criteria with no token table and no client-side token handling.
- Same `auth()` / `protectedProcedure` API for credentials and OAuth users.
- Blocking, account deletion and role changes are effective on the next request everywhere
  (tRPC, server components, `/api/auth`).

**Negative / known gaps**

- **Sign-out cannot revoke the JWT server-side.** The PO's US-03 says "the token is deleted";
  as the contract (§4, §7) states, we delete the cookie, and a copied token stays valid until
  it expires. Accepted for the MVP. Mitigations if needed later:
  - a deny-list of token ids (`jti`) checked in the `jwt` callback, or
  - a shorter `session.maxAge` (the contract's "short expiry" option).
- **Extra query per `auth()` call**: one primary-key lookup on `User` in the `jwt` callback,
  on every request that reads the session (including `/api/auth/session`). Cheap, and it is
  what makes blocking and role changes immediate. If the DB is down, the lookup fails and
  Auth.js drops the session (fails closed).
- **Account lockout**: anyone can block an account's password sign-in for one 15-minute window
  by failing 10 times on purpose. Accepted at our scale; revisit with CAPTCHA if abused.
- **No per-IP limits without `TRUSTED_PROXY_COUNT`**: with `0` (local dev, plain Docker) the
  client IP is unknown, so only the per-email limit applies. A wrong count on a deployment
  either trusts forged `X-Forwarded-For` entries (too high) or rate-limits the proxy (too low).
- **Rate limiter is per process.** Counts are lost on restart and not shared between
  instances. Fine for the single-instance staging server; a shared store (e.g. Redis/Upstash,
  as contract §9 notes) is needed before scaling. If more procedures need limits (e.g.
  `assistant.search`, contract §9), wrap it as a `rateLimitedProcedure` middleware.
- Email verification (US-06) and password reset (US-08) are post-MVP (contract §7) and not
  covered here.
- `User` type augmentation stays disabled because two `@auth/core` versions are installed;
  `JWT` is augmented in `next-auth/jwt` instead, and `role` is checked at runtime in `jwtCallback`.
